# VSIX Design Decisions

This table records accepted VSIX/TUI differences so release work does not keep reopening settled design questions. Keep it short, concrete, and limited to decisions that affect user behavior.

| Area | VSIX decision | Why this differs from the TUI | Release impact | Revisit when |
| --- | --- | --- | --- | --- |
| Scope | This repository owns the VSIX frontend release surface only. | Backend and ACP changes affect every iCode frontend and are not part of VSIX release polish. | Backend gaps are not blockers unless they break normal VSIX coding-agent workflows. | A missing backend capability becomes a confirmed blocker for core VSIX use. |
| iCode binary | Resolve iCode in this order: `chrys.binary.path`, PATH, then a bundled `extension/bin/chrys` or `extension/bin/chrys.exe` only when installed from a platform VSIX. | The TUI is launched directly by the installed CLI; the VSIX is an editor frontend that can be shipped as either a universal slim package or a platform package carrying a release-built PyApp runtime. | Universal VSIX remains slim and user-managed. Platform VSIXs can start without a separate install, but they must not download, auto-update, or hide a user-configured binary. | Product changes the managed-runtime strategy or adds more platform/arch targets. |
| Startup session | Opening iCode renders the panel immediately, warms ACP in the background, and does not call ACP `session/new`; it stays session-idle until the first prompt or explicit New Session. Startup stages and the selected working directory remain visible, and early prompt/New Session commands wait for warm-up. | The TUI engine has an internal startup session id, but ACP `session/new` is a heavier visible session lifecycle action in the VSIX. | No blank panel or false-ready state during ACP initialization, and no extra saved sessions just from opening the panel. Doctor treats no active session as normal idle. | ACP exposes a lightweight runtime-init/session-preview API with no persisted session side effects. |
| Chat panel lifetime | The extension host retains the current transcript in memory while the chat tab is closed. Reopening or reloading the webview restores messages and current tool/stream updates; explicit clear, session switch, and session restore replace that transcript. Closing chat preserves pending approval/AskUser requests and stops view-only refresh timers; reopening the same session restores the pending requests. | Editor tab lifetime is independent of the ACP session. Closing a view must not lose an ongoing response or let its callbacks update a replacement dialog. | Tab recreation needs no extra ACP session/load or private replay hook. Extension-host restart still uses the existing saved-session restoration flow. | Backend history contracts or frontend memory requirements change. |
| Multiple session tabs | Each session has one editor tab and an independent ACP process, session manager, transcript, composer draft, approval/AskUser state, usage, tools, and diagnostics. Opening an already live session reveals its existing tab or recreates its closed view. New Session and loading another session remain available during a running turn. | The IDE supports parallel tasks; a TUI screen owns one foreground conversation. Per-session processes preserve workspace and restart isolation using existing ACP contracts. | Tab titles show running, stopping, waiting for approval/answers, or completion. Background questions notify without stealing focus. Closing a tab neither cancels its task nor approves/rejects requests. Live runtimes remain until extension shutdown; window reload restores the last active saved session and other saved sessions can be reopened from the tree. | Process/memory cost warrants shared-connection multiplexing or idle-runtime eviction. |
| Approval mode before session | Changing approval mode with no active session updates the VSIX default only. | TUI approval state is bound to its running engine; VSIX may be idle before any ACP session exists. | No `No active session` errors in logs. The default applies to the next VSIX session. | Backend supports process-scoped mode state or the VSIX always has a real active session. |
| Model default | `chrys.model.profile` is applied to newly created VSIX sessions after ACP starts; empty means leave iCode model resolution unchanged. | The TUI uses iCode environment/config resolution directly. The current ACP startup path should not receive unsupported empty/default model flags. | Model selection is a VSIX new-session default, not a backend-global write. | ACP adds a supported process/session default model API that matches iCode semantics. |
| Sessions tree | Use a VS Code TreeView grouped by recency, with the current saved session pinned when available. | The TUI has function-key session screens; VS Code users expect a side tree and context menus. | Opening sessions remains available during turns; deleting a running target session is guarded regardless of which tab initiated the action. | Users need a richer session browser than VS Code TreeView can provide. |
| Session JSON | Expose structured session data through commands and Sessions tree context menus. | The TUI can render session/debug panels inline; VS Code is better at opening structured documents. | This is the accepted debug surface for session persistence mismatch. | ACP/session persistence paths change or session JSON is no longer locally discoverable. |
| Logs and Doctor | Doctor and logs focus on VSIX/TUI mismatch, ACP startup, frontend errors, operation guards, and support bundles. | The TUI debug panel can inspect broader iCode runtime state; VSIX logs should not pretend to debug the whole backend. | Doctor is release-critical for reproducible VSIX issues, but it may show IDE-native QuickPick actions. | ACP exposes richer runtime diagnostics that should be included in support bundles. |
| Local session names | `/rename`, the active chat editor toolbar, Command Palette and Sessions tree set a workspace-local display name. Empty input restores the backend-provided title. The name is used consistently in chat tabs, the tree, session pickers and the in-chat session list. | The TUI can rename a persisted backend session directly; current iCode ACP has no supported title mutation route. VSIX does not write session files or invent a private method. | Labels explicitly say local and explain that the TUI title is unchanged. Cross-client title synchronization remains a documented ACP gap. | iCode exposes a supported session-title mutation contract. |
| Prompt history search | `Ctrl+R`, `/prompts` and Command Palette search the latest 100 distinct sent text prompts retained in this VS Code workspace, filtered to the current working directory. Selecting fills the originating tab without sending; cancellation preserves its draft. | TUI has its own persistent prompt history and editor navigation. VSIX uses an IDE QuickPick and does not import TUI history. | Preserve prompt whitespace and multiline text. Cross-tab searches share workspace storage; old panel callbacks must not overwrite a replacement tab. `/history` continues to mean Session JSON. | Product needs configurable retention or a shared history protocol. |
| Clear display | `/clear` is explicitly named Clear Display. It removes frontend transcript entries and adds a notice that session context and saved history remain; `/new` is the route to a fresh context. | TUI `/clear` confirms deletion and starts a new session; deleting saved data is not implied by clearing an IDE view. | Do not invoke backend close/delete/new or reset usage and plan state. Guard the action while a turn runs. | A dedicated context-reset contract and explicit product flow are introduced. |
| Slash commands | VSIX slash commands are searchable IDE commands; unknown runtime/skill slash prompts are preserved for iCode instead of blocked. | The TUI owns the terminal-like command line; VSIX also coexists with VS Code command/search/file surfaces. | `/search`, `/grep`, `/doctor`, `/support`, `/model`, `/sessions`, and aliases must work for daily use. | A TUI command becomes core to coding-agent workflow and lacks a VSIX equivalent. |
| Composer triggers | Keep the composer hint buttons and typed triggers for `/`, `@`, `#`, and `!`. They are part of the coding input surface, not the TUI footer shortcut set. | VS Code users still benefit from visible file/agent/shell/slash affordances in the input area. | Composer hints remain visible and actionable; typed triggers continue to work. | Hints become visually noisy after a better discoverability path exists. |
| TUI shortcut buttons | Do not render or bind TUI F-key/footer shortcut buttons in the VSIX. Move the same non-composer capabilities to the iCode TreeView content actions, TreeView title menu, Command Palette, slash commands, or session context menus. | VS Code already has Command Palette, TreeView, menus, and native panels; duplicating TUI footer chrome adds clutter and maintenance cost. | F1/F2/F4/F6/F9/F10/F12 footer controls are intentionally absent and not release blockers, but their capabilities must remain reachable elsewhere. | A shortcut becomes necessary for core coding flow and has no slash or VS Code-native entry point. |
| User turn numbering and injections | Keep turn numbers in the VSIX sidebar message list only. Do not render turn numbers in the main chat transcript, and do not mutate prompt text into `1. text`. Mid-run injected user messages are not numbered; they use an ASCII child marker (`└─` / `└ ❯`) in the same prefix column as the turn number so they read as subordinate messages. | The TUI transcript uses terminal-style visual chrome, but the VSIX main chat needs cleaner reading flow while the sidebar acts as the scan/navigation surface. Prompt text mutation changes what iCode sees and can affect model behavior. | Sidebar normal user turns are numbered for navigation; injected messages are unnumbered and marked; main chat user bubbles are unnumbered. | A backend protocol starts carrying display-only turn labels and injection hierarchy metadata. |
| Terminal mode | `!` opens/reuses the VS Code integrated terminal in the workspace. | The TUI embeds a PTY panel; VS Code already has a mature terminal. | Full embedded shell-mode parity is not required for release. | IDE terminal integration cannot support a required iCode workflow. |
| File references | `@` uses VS Code file pickers/search and can insert references into the composer. | The TUI renders file navigation inside its own input surface. | Native file navigation is preferred if it remains fast and workspace-scoped. | File mention behavior diverges from what iCode prompt handling expects. |
| Images | Paste/drop images show preparation/compression progress in the composer; actual image input depends on the active model profile advertising vision support. | The TUI and VSIX have different paste/drop surfaces. | User-visible progress and unsupported-image feedback are required; perfect TUI mechanics are not. | ACP image capability metadata changes or compression becomes backend-owned. |
| Right-click copy | Use VS Code/webview context actions for selected text, whole messages, tool cards, session ids, and support summaries. | The TUI has terminal selection and function-key flows. | Copy actions must be easy and useful for mismatch debugging. | Users cannot copy the information needed for support/debug workflows. |
| Themes | Support coherent VSIX themes, especially `chrys` and `chrys-ansi`; do not chase pixel-perfect identity for every TUI theme. | Terminal ANSI rendering and CSS theming have different constraints. | The composer, status area, sidebar, and approval badge must feel familiar and readable. | A supported TUI theme becomes unreadable or product requires exact brand parity. |
| Webview visual language | Keep the chat webview as a TUI-inspired bordered cockpit: compact panels, status-first tool cards, terminal composer, sidebar scan surface, and accessible modal dialogs. Avoid reverting to generic rounded web cards or pixel-perfect TUI footer chrome. | The VSIX must feel familiar to TUI users while still fitting VS Code webview constraints, keyboard navigation, and editor-native actions. | Chat bubbles, tool calls, sidebar tabs/messages, approval/ask-user dialogs, and composer styling should share the iCode TUI tokens and bordered-panel hierarchy. | Product adopts a new design system for all iCode frontends or VS Code webview constraints change substantially. |
| Companion | Companion is VSIX-owned: local animated WebP/PNG assets, safe card packs, daily 09:00 summon, collection state, static rarity, iCode-usage growth levels, and pet/mute/rename/info/direct-address interactions. The redesigned Buddy tab centers the pixel companion directly on the sidebar background, without a decorative frame or platform, with workflow presence, replies and real XP progress. Clicking the character pets it; collection, summon, mute and rename use a compact options menu backed by the existing local commands. Slash commands such as `/companion collection` and `/companion summon` remain available. Do not call unsupported Buddy ACP methods or depend on iCode hook configuration. | iCode backend Buddy will not evolve, while the VSIX webview can render a local workflow pet from VSIX/ACP-visible state without changing what iCode receives. The options menu keeps management secondary to the character, while keyboard focus, in-progress name edits and reduced-motion preferences survive runtime updates. | Companion can ship as an editor-local feature when it stays safe, local, quiet by default, and does not block chat/session flows. | Product decides Companion should become a backend-synchronized cross-client feature or needs a richer dedicated management surface. |
| iCode ACP Extension Route Names | The VSIX sends top-level JSON-RPC extension method names with the underscore prefix accepted by the ACP router, such as `_chrys/session_runtime`, `_session/mutations`, `_settings/options`, and `_profiles/models/list`. Backend `ext_method` documentation may describe logical names without the prefix, such as `chrys/session_runtime`; those are not the top-level VSIX route strings. | iCode `v0.22.5` still routes the underscore-prefixed top-level names, while direct `chrys/session_runtime` returns method-not-found in a stdio smoke. | Do not rename client requests from `_chrys/*` / `_session/*` to unprefixed logical names unless a live stdio smoke proves the top-level route changed. | iCode advertises extension capabilities/versioning or the ACP router changes its public method normalization contract. |
| ACP protocol gaps | Missing ACP capabilities are tracked, but not release blockers by default. | VSIX can use editor-native alternatives for some TUI behaviors. | Block only when a gap breaks normal coding-agent use or reproducible diagnostics. | A gap prevents core chat, tools, approvals, sessions, model selection, or support debugging. |
| Workspace selection | Prefer the active editor's workspace in a multi-root window, then the first workspace folder, then the active file directory; ask only when none exists. CWD and `/cd` without a path offer current VS Code workspace folders by name and full path, plus browsing elsewhere; cancellation keeps the current directory. Keep the resolved path visible in startup and chat chrome. | An IDE can have multiple workspace roots and users need to know exactly where agent tools will run. | ACP starts with the same absolute path shown in the UI and passed through `-C`; changing it while session-idle restarts the workspace-scoped backend. | ACP supports multiple simultaneous workspace roots or VS Code adds a stronger per-chat workspace primitive. |
| Auxiliary dashboard | The Messages/Sessions/Context/Debug dashboard is manually collapsible at every width. It is inline by default above 760px, closed by default below that threshold, and opens as an overlay drawer on narrow editors. | Secondary information must never consume half of a narrow chat, while IDE users still need direct access to ACP plan, sessions, runtime inventory, and diagnostics. | The user preference persists; narrow auto layout never stacks the dashboard below the conversation. | User research supports a different breakpoint or a VS Code-native view fully replaces the in-chat dashboard. |
| Running status | Render task waiting/Thinking as prominent session-frame chrome and keep Agent loading/readiness transient; only Agent-load failures remain in the transcript. | The TUI uses a loading surface and status flash rather than treating readiness as conversation content. | Empty/waiting chat states remain visibly active without polluting saved conversation history. | ACP adds a unified operation-status model that supersedes these lifecycle events. |

When adding a new row, prefer an existing VS Code-native workflow unless it changes what iCode receives, hides a core state, or creates unexpected persisted sessions.

### Configuration surfaces

Profile editors use searchable navigation beside a form, with a distinct in-use badge and collapsed advanced connection fields. At narrow widths, the navigation moves above the form. The settings management page uses searchable rows. These surfaces retain the existing local profile and ACP contracts; workspace directory selection, quick model switching, and approval-mode selection remain editor-native.

### Welcome branding

`chrys.ui.brand` selects the welcome wordmark and icon: `icode` (iCode / iC) by default, or `chrys` (iCode / C). Clicking the welcome brand opens the editor-native picker and saves the choice; changes in editor settings update the page immediately. This visual preference does not change the extension identity, ACP runtime, or connected `iCode CLI vX.Y.Z` label.

### Multi-session ownership

`ExtensionRuntime` instances own session state. The `rt` facade resolves an explicitly bound asynchronous scope; `withRuntime`/`bindRuntime` preserve that scope across awaits. ACP and process callbacks bind at registration, webviews bind to their constructor owner, and IDE command dispatch snapshots the initiating runtime. Focus changes only choose the target of subsequent commands. Keep all new asynchronous entry points bound; never route a delayed response using whichever tab happens to be active. Diff URIs include the tab identity and message IDs remain monotonic across resets.

Each open runtime starts its own installed iCode ACP process. Sessions using the same directory still share the actual filesystem and user-level profile/configuration files. Processes stop on extension shutdown; closing a view keeps its runtime available for background work and pending questions.

## iCode rename

Product copy and package metadata use iCode. Retain `chrys.*` command, configuration and storage identifiers, theme IDs, bundled launcher names and `_chrys/*` routes for compatibility. Prefer `icode` on PATH, then `chrys`. The new extension ID does not automatically migrate old extension-scoped state; users must disable the old extension to avoid duplicate commands. CD reads public offline assets from openJiuwen-ai/iCode.
